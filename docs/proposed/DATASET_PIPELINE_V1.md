# VECTOR Dataset Pipeline v1

**Status:** PROPOSED  
**Version:** 1.1  
**Authority Scope:** DATASET_PIPELINE  
**Approved By:** pending project_owner approval  
**Supersedes:** DATASET_PIPELINE_V1 v1.0 proposal  
**Scope:** SCMDB upstream detection, validation, completeness filtering, canonical catalog extraction, standardization, LIVE/PTU dataset revisioning, optimized publication and channel-scoped state boundaries

## 1. Purpose

This specification defines how VECTOR detects, validates, classifies, transforms and publishes Star Citizen reference data from the approved SCMDB upstream while keeping mutable game state and VECTOR-persistent state separate.

The canonical processing sequence is:

```text
Update Detection
-> Download
-> Validation
-> Completeness Filter
-> Build / Channel Check
-> Data Extraction
-> Canonical Catalog Resolution
-> Data Standardization
-> Candidate DB Update
-> Verification
-> Atomic Promotion
```

Dataset Revision is metadata generated by this pipeline. It is not a second dataset-build pipeline.

## 2. Architecture goals

The pipeline and database model optimize for:

- strict LIVE/PTU data-context isolation;
- minimal duplicate storage;
- stable canonical entity identities;
- deterministic catalog and taxonomy resolution;
- targeted game-state wipes;
- bounded database queries;
- bounded API payloads;
- token-efficient AI retrieval;
- source provenance and reversible interpretation;
- last-known-good preservation;
- independent data updates without application releases.

No website module should need to crawl or deserialize the complete SCMDB dataset to answer a bounded application request.

## 3. Source and provenance boundary

SCMDB is an approved read-only upstream source for VECTOR reference data.

VECTOR preserves enough raw source identity and provenance to distinguish:

```text
Source Truth
Canonical VECTOR Entity
Dataset-revisioned Representation
Derived / Resolved Value
Mutable Game State
```

VECTOR must not silently rewrite source classification. Source fields remain traceable even when a VECTOR resolver assigns a different catalog category.

## 4. Channel model

The canonical game-data channels are:

```text
LIVE
PTU
```

Each channel maintains an independent:

- upstream revision state;
- Star Citizen build identity;
- candidate dataset;
- dataset revision;
- publication state.

LIVE and PTU use the same logical data contract but can contain different entities, values and active revisions.
In v1, mutable game state is the Production User State defined by `DATA_CONTEXT_MODEL_V1.md`, not a separate state store per dataset channel. A PTU Preview may read that state as a selection/input context but must not mutate it or assert PTU-native mutable state.

## 5. Core invariants

### 5.1 No LIVE/PTU data mixing

A calculation or reference lookup must resolve against exactly one active dataset context unless an explicitly approved comparison workflow requests both contexts as separate inputs.
For a PTU Preview, Production User State may be a separate read-only selection/input context; all channel-dependent reference data and derived values still come exclusively from the PTU dataset. Production User State is not LIVE reference data and does not authorize LIVE/PTU reference-data mixing.

```text
LIVE candidate -> LIVE revision
PTU candidate  -> PTU revision
```

A PTU-only upstream change must not rebuild or mutate LIVE.
A LIVE-only upstream change must not rebuild or mutate PTU.

### 5.2 One canonical pipeline

LIVE and PTU use one processing contract.

Channel-specific adapters are permitted only when upstream structures require them. All adapters must produce the same canonical VECTOR domain contract.

### 5.3 No-Guess

If VECTOR cannot determine a mandatory source identity, build, channel, entity relation, classification or required value with sufficient confidence, the value remains unresolved.

Allowed states include:

```text
SOURCE_EXACT
RULE_RESOLVED
REVIEW_REQUIRED
SOURCE_DATA_MISSING
QUARANTINED
```

Ambiguity never becomes a guessed authoritative value.

### 5.4 Last-known-good

A failed candidate never replaces the current active dataset.

```text
candidate fails mandatory gate -> REJECTED / BLOCKED
current active revision         -> remains ACTIVE
```

## 6. Update Detection

Update Detection determines independently:

```text
live_changed = true | false
ptu_changed  = true | false
```

Execution matrix:

```text
LIVE unchanged + PTU unchanged -> NO_CHANGE
LIVE changed   + PTU unchanged -> LIVE only
LIVE unchanged + PTU changed   -> PTU only
LIVE changed   + PTU changed   -> both independently
```

A generic upstream repository commit is not sufficient reason to rebuild both channels.

### 6.1 Trigger policy

Preferred long-term behavior:

```text
trusted upstream event/webhook
-> immediate Update Detection
```

Until an authoritative event source is verified:

```text
scheduled polling
-> lightweight Update Detection
```

Manual `workflow_dispatch` remains available for controlled testing and recovery.

A schedule firing does not itself authorize a full dataset rebuild.

## 7. Download

Download executes only for channels selected by Update Detection or explicitly authorized manual execution.

Downloaded source is staged candidate material.

Download must not mutate:

- active reference revisions;
- mutable player/game state;
- persistent VECTOR state.

A channel-specific download failure blocks only that channel unless shared infrastructure integrity is uncertain.

## 8. Validation

Validation confirms that candidate source material is structurally usable before semantic processing.

Validation includes, where applicable:

- mandatory files exist;
- JSON parses correctly;
- required top-level structures exist;
- mandatory entity identifiers are present;
- relationships can be inspected;
- clearly corrupt input is rejected;
- applicable crafting, blueprint, item and stat sanity checks pass.

Validation success does not prove semantic completeness.

## 9. Completeness Filter

The Completeness Filter is mandatory for LIVE and PTU.

It determines whether source records are safe to publish when mandatory data or relationships are incomplete, orphaned or contradictory.

Allowed deterministic outcomes:

```text
ACCEPT
FILTER_OUT
QUARANTINE
BLOCK_DATASET
```

The filter never invents missing values.

Filter evidence should preserve, where applicable:

- source entity identity;
- source revision;
- channel;
- reason code;
- rule/resolver version;
- source path.

## 10. Build / Channel Check

Before catalog extraction, VECTOR verifies:

```text
channel = LIVE | PTU
build   = verified Star Citizen build
```

A mismatch blocks publication:

```text
EXPECTED LIVE / ACTUAL PTU -> BLOCK
EXPECTED PTU  / ACTUAL LIVE -> BLOCK
```

VECTOR does not automatically move candidates between channels.

## 11. Canonical data layers

VECTOR uses separate logical layers instead of treating a complete SCMDB JSON tree as an application database.

### 11.1 Raw Source Layer

Purpose:

- provenance;
- debugging;
- reproducibility;
- resolver reprocessing.

Conceptual content:

```text
source_record_id
source_system
source_name
source_revision
identity_namespace
source_entity_id
source_class_path
content_hash
raw artifact reference / payload
```

Raw source data is not the normal frontend query surface.

### 11.2 Canonical Entity Layer

Represents a stable VECTOR concept independent from one particular build.

Conceptual content:

```text
canonical_entity_id
entity_kind
preferred_name
product_family_id / base_entity_id
identity_status
```

Source UUIDs, display names and catalog paths must not be used interchangeably with the canonical VECTOR primary identity.

### 11.3 Dataset Revision Layer

Contains values that may vary by Star Citizen build/channel.

Conceptual content:

```text
canonical_entity_id
dataset_revision_id
source_entity_id
source_type
source_subtype
manufacturer_id
size_value
revision_properties
resolution_status
```

### 11.4 Mutable Game State Layer

In v1, this layer contains the single Production User State, including mutable player/game-derived state such as inventory, in-game ownership and Actual Loadouts. Its identity is independent from the selected reference dataset revision.

A PTU Preview may read Production User State as a read-only selection/input context with one PTU Reference Dataset. It must not mutate that state or represent it as PTU-native ownership, inventory, wallet, reputation or other PTU-native mutable state. `RESULT_CONTEXT_PTU_PREVIEW` and `PTU_NATIVE_STATE` are distinct contexts; PTU-native mutable state is a future extension, not an active v1 assumption.

The logical model can support a future `PTU_NATIVE_STATE` as an independently channel-isolated state context without changing canonical entity identity or reference-data revision semantics. That extension requires explicit implementation and governance before its state or wipe operations are active.

### 11.5 Persistent VECTOR State Layer

Contains VECTOR-owned state that survives ordinary Star Citizen wipes, including user/account relationships, Crew state, saved plans/templates, settings, audit and provenance history.

## 12. Canonical Catalog

VECTOR maintains a canonical application catalog above the raw SCMDB representation.

The catalog provides stable navigation and retrieval domains such as:

```text
fps_item.weapon.rifle
ship.component.quantum_drive
ship.component.shield
armor.helmet
crafting.material
```

A catalog path is a navigation/classification value, not an entity primary key.

### 12.1 Source Classification vs VECTOR Taxonomy

VECTOR stores both:

```text
source classification
VECTOR classification
```

Source fields such as item family, attach type, attach subtype, source class path and upstream categories remain preserved.

VECTOR taxonomy may resolve these fields into stable application categories without deleting the original classification.

### 12.2 Representative supported pattern

A source item with structured evidence equivalent to:

```text
family = shipcomponent
attach_type = QuantumDrive
size = 3
name = TS-2
```

can produce a presentation path equivalent to:

```text
Ship.Component.QuantumDrive.Size3.TS-2
```

The path is built from structured classification and entity relations. It is not parsed back as the sole source of truth.

## 13. Taxonomy tree

The catalog taxonomy is hierarchical.

Conceptual category record:

```text
catalog_category_id
parent_category_id
category_code
catalog_path
depth
```

Categories should be stable application concepts rather than direct copies of potentially unstable upstream labels.

Taxonomy changes require versioned rules when they affect deterministic extraction or application behavior.

## 14. Category assignments

One entity can have multiple useful category associations.

Conceptual assignment:

```text
canonical_entity_id
catalog_category_id
assignment_role
assignment_source
resolution_status
rule_version
```

The v1 assignment role set is exactly:

```text
PRIMARY
SECONDARY
FUNCTIONAL
```

The Canonical Data Model is authoritative for category-assignment semantics and defines the complete v1 role set. Variant and compatibility semantics are Relations (for example, `VARIANT_OF` and `COMPATIBLE_WITH`), not taxonomy/category assignment roles. This pipeline may process and publish those structures but does not independently define their semantic authority.

Ambiguous assignments remain `REVIEW_REQUIRED` or `QUARANTINED` rather than becoming authoritative.

## 15. Base products and variants

VECTOR supports relationships between a base product/family and named variants.

Example conceptual relationship:

```text
Killshot Rifle
├── base/default entity
└── Dominion Camo variant
```

Variant status must come from explicit source evidence or deterministic resolver rules.

Tokens such as `DefaultSkin`, `Payback`, color names, editions or suffixes are not automatically treated as skins or variants solely because of their names.

The original source entity remains independently identifiable even when grouped under a base product.

## 16. Faceted classification

Hierarchy and facets serve different purposes.

Taxonomy answers:

```text
Where does this entity belong?
```

Facets answer:

```text
Which structured properties can be filtered or compared?
```

Examples:

```text
size
manufacturer
attach_type
attach_subtype
grade
class
weapon_family
armor_slot
material_family
```

Frequently filtered facets should be represented as structured/indexable fields or relations, not repeatedly extracted from raw JSON or catalog path strings at request time.

## 17. Data Extraction

Data Extraction converts validated source structures into domain-specific intermediate records.

Domains may include:

- items;
- weapons and fire modes;
- armor;
- ship components;
- ships;
- crafting blueprints;
- materials;
- mining data/equipment;
- manufacturers;
- locations;
- other approved SCMDB-backed domains.

Extraction preserves source provenance.

Extraction must not mix channels.

## 18. Data Standardization

Standardization maps extracted records to the canonical VECTOR domain model.

Responsibilities include:

- canonical entity resolution;
- normalized names and types;
- normalized units;
- source-ID mapping using `source_system`, `identity_namespace` and `source_entity_id`;
- manufacturer resolution;
- size/facet resolution;
- base/variant relationships;
- taxonomy assignments;
- relation extraction and publication under the Canonical Data Model's semantic authority;
- resolver-compatible property values;
- provenance;
- build/channel metadata;
- dataset revision metadata.

Unresolved values stay unresolved.

## 19. Database topology

### 19.1 Preferred baseline

The preferred v1 baseline is one PostgreSQL/Supabase database with normalized domain tables and strong logical separation.

The logical model is:

```text
Shared Canonical Catalog
+
Dataset-revisioned Reference Data
+
Production User State (v1 mutable game state)
+
Persistent VECTOR State
```

This avoids unnecessary full duplication of stable canonical entities while preserving strict LIVE/PTU values and state boundaries.

### 19.2 Dataset context

Reference values specific to a build are associated with `dataset_revision_id`.

Each dataset revision identifies its channel and build.

Application queries resolve against one explicit active dataset revision for the selected context.

### 19.3 Physical partitioning

The implementation may later introduce PostgreSQL partitioning, separate schemas or another physical optimization after real query volume and operational requirements are measured.

Physical optimization must preserve the canonical logical model and channel isolation.

Two fully duplicated databases are not the default requirement of this specification.

## 20. Query and index model

Application features use bounded domain queries.

Examples:

```text
Inventory
-> user/context inventory rows
-> bounded canonical item IDs
-> active revision projection
-> required locations only
```

```text
Fleet
-> user ship instances/plans
-> bounded ship/component entities
-> active revision properties
```

```text
Crafting
-> selected blueprint
-> material requirements
-> bounded inventory availability
```

```text
Comparison
-> taxonomy/facets
-> selected entities
-> selected stat families
```

Exact database indexes are not frozen in this specification. Indexes must be designed against measured query patterns and acceptance tests rather than speculative full-dataset indexing.

## 21. Read Models and payload optimization

Website modules and AI retrieval should use purpose-built projections instead of raw SCMDB payloads.

Potential read models include:

```text
catalog_item_summary
inventory_item_view
ship_component_catalog_view
weapon_comparison_view
crafting_blueprint_view
```

A read model should expose only fields required by its use case.

Example component summary:

```text
canonical_item_id
name
manufacturer
size
selected component stats
active_dataset_revision
```

Read models may use normal views, RPCs, bounded queries or materialized representations where justified by measured performance.

A dataset promotion must define how affected cached/materialized read models become consistent with the newly active revision before the revision is considered fully available.

## 22. Token-efficient AI retrieval

AI features must not receive full raw datasets when a bounded domain response is sufficient.

Preferred retrieval flow:

```text
intent/domain
-> taxonomy/facets
-> bounded entity IDs
-> bounded field projection
-> compact DTO
-> AI context
```

Token efficiency is achieved through retrieval scope and projections, not by dropping provenance or correctness-critical fields.

## 23. Candidate DB Update and atomic publication

Database publication is candidate-first:

```text
Download
-> Validate
-> Completeness
-> Build/Channel Verify
-> Extract
-> Catalog Resolve
-> Standardize
-> Stage Candidate
-> Verify Candidate
-> Refresh/prepare affected read models
-> Atomic Promote
```

The application must never observe a half-published dataset.

If publication fails:

```text
new candidate -> NOT ACTIVE
previous active revision -> remains ACTIVE
```

A LIVE and PTU candidate can have independent success/failure results.

## 24. Dataset Revision

Dataset Revision identifies the published reference-data state produced by one successful channel pipeline execution.

It records at least:

- VECTOR dataset schema/version context;
- Star Citizen build;
- channel;
- upstream revision/provenance;
- applicable pipeline/filter/resolver/taxonomy versions;
- publication state.

Combined internal identifier:

```text
Vector_{VersionNumber}_SC_{Build}
```

Example:

```text
Vector_1.3.1_SC_4.10.2-LIVE.12881860
```

Normal UI context remains compact:

```text
LIVE 4.10.2
PTU 4.10.3
```

VECTOR app/code version and dataset updates remain decoupled.

## 25. Dataset states and idempotency

Candidate states may include:

```text
DETECTED
DOWNLOADED
VALIDATED
FILTERED
CHANNEL_VERIFIED
EXTRACTED
CATALOG_RESOLVED
STANDARDIZED
STAGED
VERIFIED
ACTIVE
REJECTED
```

Only `ACTIVE` is authoritative for normal reference lookups.

Reprocessing the same upstream revision under unchanged transformation rules must not create a duplicate logical active dataset.

A pipeline-rule, resolver, taxonomy or completeness-rule change may require explicit reprocessing even when the upstream source revision did not change.

## 26. Mutable Game State

In v1, Production User State is the mutable game-state context and is stored separately from reference data. It is not duplicated or switched when the active reference Dataset Context changes.

Examples include:

- inventory positions;
- inventory lots;
- quantities;
- storage assignments;
- movable game item instances;
- in-game-owned ship instances;
- Actual Loadouts;
- game-derived ownership.

Mutable rows reference canonical entities and the Production User State context. Dataset-derived interpretation resolves against exactly one selected active dataset revision; a PTU Preview reads Production User State inputs without changing them or asserting PTU-native state.

Mutable state must not duplicate complete item definition/stat payloads when a canonical/revision reference is sufficient.

`PTU_NATIVE_STATE` is a future extension. If explicitly implemented and governed by VECTOR rules, its mutable rows must have an independently identifiable PTU state context and must remain isolated from Production User State. This extension does not require redesigning canonical entities or weakening LIVE/PTU reference-data isolation.

## 27. Persistent VECTOR State

Ordinary Star Citizen wipes do not remove VECTOR-persistent application state such as:

- authentication identity;
- user profile;
- Game Identity relationship history;
- Crew membership and roles;
- Fleet Plans;
- saved Loadout Templates;
- settings;
- audit/provenance history;
- ownership whose approved source survives the applicable game wipe.

## 28. Wipe boundary

```text
Dataset Update != Game Wipe
```

Reference/catalog data is not a normal game-wipe target.

### 28.1 PTU-native game-state wipe

A PTU dataset activation or PTU Preview does not create or target mutable PTU state in v1. A PTU-native game-state wipe becomes applicable only after `PTU_NATIVE_STATE` is explicitly implemented and governed by VECTOR rules. If introduced, it may target only its approved PTU-native state domains and must not delete:

- Production User State;
- canonical catalog;
- LIVE/PTU reference revisions;
- VECTOR Persistent State.

### 28.2 LIVE wipe

A LIVE game wipe can target only the explicitly approved domains of the v1 Production User State, without deleting:

- canonical catalog;
- LIVE/PTU reference revisions;
- VECTOR Persistent State.

### 28.3 Fine-grained wipe scopes

Potential future scopes include:

```text
FULL_GAME_STATE
INVENTORY_ONLY
OWNERSHIP_ONLY
LOADOUT_ONLY
```

Exact wipe commands and dependencies are governed by the approved Game Wipe specification.

### 28.4 Stats are reference data

SCMDB-derived item/component/weapon/ship statistics are reference data and are not deleted as ordinary movement/game-state data during a wipe.

## 29. Failure isolation and concurrency

Failure in one channel must not invalidate the other channel.

Conceptual locks:

```text
dataset-pipeline-live
dataset-pipeline-ptu
```

Conflicting same-channel promotions cannot run concurrently.

LIVE and PTU processing may run independently when shared catalog operations and atomic promotion can be kept safe.

## 30. Provenance and classification audit

Every active revision and resolved catalog representation must retain sufficient provenance to explain:

- which upstream record supplied the value;
- which build/channel applied;
- which resolver/taxonomy rule was used;
- whether the result was exact, resolved, missing, ambiguous or quarantined;
- which pipeline execution published the active value.

Source classification is never destroyed when VECTOR resolves a derived classification.

## 31. Migration of current SCMDB workflow

The existing workflow:

```text
.github/workflows/sync-scmdb-data.yml
```

contains useful source retrieval, validation, sanity checks, mirror/provenance behavior and manual execution that should be preserved where still applicable.

The daily full-mirror schedule must not remain the publication decision model.

Target behavior:

```text
frequent lightweight Update Detection
-> changed channel only
-> one canonical pipeline
-> normalized candidate publication
```

Git diff may remain useful for mirror/audit purposes but is not authoritative channel revision detection.

## 32. Acceptance Criteria

DATASET_PIPELINE_V1 is ready to freeze only when VECTOR demonstrates that:

- LIVE and PTU updates are detected independently;
- unchanged channels do not run the full pipeline;
- channel-only updates cannot mutate the other channel;
- malformed mandatory source data is rejected;
- Completeness Filter applies to LIVE and PTU;
- ambiguous or incomplete values are not guessed;
- Build/Channel Check occurs before extraction/publication;
- raw source identity/provenance is preserved;
- canonical entities are not keyed solely by display names or catalog paths;
- source classification and VECTOR taxonomy remain distinguishable;
- base/variant grouping uses deterministic evidence;
- multiple category assignments are supported;
- frequently filtered facets are structured/indexable;
- build-specific values use dataset revision context;
- one normalized logical model supports LIVE/PTU without mandatory full physical duplication;
- application modules use bounded queries/read models rather than full-dataset crawling;
- AI retrieval uses bounded field projections;
- publication is candidate-first and atomic;
- last-known-good remains active after failure;
- read-model consistency is included in promotion semantics;
- identical unchanged processing does not create duplicate active revisions;
- transformation-rule changes can explicitly trigger safe reprocessing;
- Production User State is separated from Reference Data and is the only mutable game-state context required in v1;
- PTU Preview reads Production User State without mutation or PTU-native ownership/state assertions;
- PTU-native mutable state and its wipe operations remain future extensions until explicitly implemented and governed by VECTOR rules;
- any future PTU-native state is independently channel-isolated from Production User State;
- canonical catalog/reference stats are excluded from ordinary wipe scope;
- VECTOR Persistent State survives ordinary game wipes;
- provenance explains every active resolved classification/value.

## 35. Proposed Decision

VECTOR Dataset Pipeline v1.1 is **PROPOSED**.

It becomes eligible for FROZEN only after:

- LIVE/PTU revision detection is verified;
- Completeness Filter rules are defined;
- canonical identity/taxonomy/facet rules are validated against representative SCMDB families;
- normalized database design and query performance are tested;
- catalog/source-classification conflict behavior is tested;
- candidate publication and rollback are validated;
- channel-scoped wipe boundaries are verified against the Game Wipe model;
- the existing SCMDB workflow is migrated to this contract;
- `RULE_INDEX.md` is updated to reflect PROPOSED and later FROZEN status;
- review on `develop` is complete;
- approval by `project_owner`;
- merge through the normal VECTOR governance process to `main`.
